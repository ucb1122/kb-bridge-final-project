# 뜨는 상권 개발·트러블슈팅 기록

> 기록 기준: 2026년 10월 23일. 이 문서는 사용자와 서울시 상권분석서비스 화면을 대조하며 진행한 **뜨는 상권** 구현 과정을 정리한다. 수치는 대화에서 공유한 2026년 2분기 화면과 당시 로컬 데이터 기준이다. 공개 데이터나 원본 사이트가 갱신되면 다시 검증해야 한다.

## 1. 목표와 작업 흐름

서울시 상권분석서비스의 뜨는 동네·뜨는 상권 화면을 참고해 지도 순위와 지역별 분석 보고서를 만들었다. 처음에는 보유한 원본 ZIP·CSV를 SQLite에 넣고 지표를 합산해 순위를 계산했다. 이후 원본 서비스와 나란히 비교하면서 다음 순서로 보완했다.

1. 상권별 ZIP과 행정동별 CSV를 구분해 적재하고, 점포수·추정매출·유동인구·상주인구의 원본 수치를 확인했다.
2. 지도 배지와 호버 경계를 연결하고, 순위 목록·배지·보고서가 같은 지역을 가리키도록 수정했다.
3. 원본 화면과 반복해서 달라진 순위의 기준을 확인해 최신 기본 순위 스냅샷을 만들었다.
4. 공식 보고서와 로컬 보고서의 **단위·분모**를 맞추고, 같은 단위여도 원천값이 다른 사례를 따로 처리했다.
5. 상세조건의 집계·정렬을 API까지 연결하고 기본 선택값과 업종 버튼 모양을 원본 화면에 맞췄다.
6. 사례별 회귀 테스트를 추가했다.

화면에서 지역을 선택하면 `frontend/pages/rising/main.js`가 `/api/rising/report`를 요청한다. 서버는 `data/commerce.sqlite`의 지역·분기·업종 자료와 공식 화면 스냅샷을 조합하고, `report-view.js`와 `full-report.js`가 요약과 상세 보고서를 그린다. Ollama를 사용할 수 있으면 종합의견을 생성하고, 사용할 수 없으면 CSV에 근거한 요약을 표시한다.

## 2. 데이터가 충분해 보였는데도 값이 달랐던 이유

사용자는 서울시 사이트의 데이터 출처 목록에 있는 자료를 이미 폴더에 넣었다고 생각했다. 실제로는 **출처 목록**, **내려받은 파일의 범위**, **공식 보고서의 가공 지표**가 서로 달랐다.

| 구분 | 프로젝트에서 사용하는 자료 | 확인한 범위 |
| --- | --- | --- |
| 뜨는 상권 | `data/raw/seoul_public_data.zip` 안의 상권별 CSV | 상권별 점포·매출·인구 및 일부 세부 지표 |
| 뜨는 동네 | `backend/scripts/fetch-dong.py`로 받은 행정동별 점포·추정매출·길단위 유동인구·상주인구 CSV | 행정동별 기본 지표와 제공된 세부 열 |
| 기본 순위 | 서울시 `getNewTrdarList.json` 응답을 저장한 `data/official-rankings-20262.json` | 최신 기준분기의 기본 조건 TOP 10 순서, 표시값, 증감률, 분석 면적 |
| 분석보고서 표시값 | 화면과 직접 대조한 `data/official-report-sales-20262.json` | **확인된 일부 지역**의 점포당 월평균 매출 및 증감액 |

상권별 ZIP만으로 행정동 보고서의 모든 지표를 채울 수는 없다. 서울시 사이트의 데이터 출처 페이지는 서비스에 활용하는 여러 DB를 설명하지만, 해당 목록이 로컬 ZIP에 모든 DB와 같은 형태로 들어 있다는 뜻은 아니다. 특히 카드사 결합·보정이 적용된 공식 추정매출은 공개 CSV 합계와 일부 지역에서 다르다. 그래서 공개 원본에서 직접 계산한 값과 공식 화면에서 확인한 값을 화면과 문서에서 구분한다.

적재 과정은 `backend/scripts/import-raw.py`, `backend/scripts/import-details.py`에 있다. 업종별 점포수와 매출금액은 지역·분기별로 합산한다. 자료가 없는 직장인구·소비·임대시세·3년 생존율 등은 행정동 보고서에서 임의로 채우지 않는다. 원본 ZIP·행정동 CSV·생성 DB는 Git에 올리지 않는다.

별도의 정규화 CSV를 사용할 때는 `data/csv/`에 UTF-8 파일을 두고 `npm run import:csv`를 실행한다. 기본 열은 `quarter,kind,metric,region_code,region_name,district,value`이며 `lat,lng`는 선택 열이다. `quarter`는 `20262` 같은 분기 코드, `kind`는 `dong` 또는 `area`, `metric`은 `stores`, `sales`, `footfall`, `residents` 중 하나다. 제공처마다 열과 집계 방식이 달라 원본 CSV를 이 형식에 맞게 변환해야 한다.

## 3. 지도 원, 호버 경계와 순위가 어긋난 문제

### 지도 표시

처음에는 마우스를 올릴 때 퍼지는 원의 느낌은 좋았지만 안쪽 배지와 바깥쪽 표시가 맞지 않았다. 지도 배지는 지역의 중심 좌표에 배치되고, 실제 행정동은 다각형 경계로 표시되므로 **원 자체가 행정동의 형상이나 면적과 일치하는 지도 데이터는 아니다.** 이후 호버·선택 상태의 배지와 경계 스타일을 정리하고, 지도에 올린 배지·목록·보고서가 같은 코드와 순위를 사용하도록 했다. 현재 경계 호버는 `frontend/pages/rising/main.js`의 `drawBoundaries`, `updateBoundaryStyles`가 처리한다.

행정동 경계는 [vuski/admdongkor의 2026-04-01 자료](https://github.com/vuski/admdongkor)를 참고한다. 통계 분기와 경계 자료의 코드 버전이 다르면 일부 지역은 경계 표시가 빠질 수 있다. 원형 배지는 순위를 읽기 쉽게 하는 시각 요소이며 실제 상권 반경을 뜻하지 않는다.

### 순위 역전

강남구의 4·5위, 8·9위와 중랑구의 3·4위, 8~10위 등에서 원본 화면과 순위가 반복해서 달랐다. 초기 구현은 로컬 CSV의 현재값과 전분기 값을 합산해 증감률을 계산하고 정렬했다. 원본 사이트는 별도의 순위 응답과 표시 정밀도·동률 처리 기준을 사용하므로 이 방식만으로 항상 같은 순서를 만들 수 없었다.

**해결:** `backend/scripts/sync-official-rankings.js`가 서울시 순위 응답을 지역 유형·지표·자치구별로 읽어 `data/official-rankings-20262.json`에 저장한다. `backend/server/data.js`는 최신 기본 조건에서 해당 순서를 우선 적용한다. 목록과 지도 배지는 동일한 API 배열의 순서로 번호를 붙인다. 스냅샷을 적용할 수 없는 다른 분기·상세조건에서는 로컬 CSV로 계산한 순위임을 출처에 표시한다.

`tests/rankings.test.js`는 강남구와 중랑구의 알려진 순서를 지역 코드로 검사한다. 이 검증은 **테스트한 조건의 순서**를 확인하는 것이며, 모든 필터 조합을 서울시 화면과 대조했다는 뜻은 아니다.

## 4. 매출·유동인구·상주인구가 달랐던 문제

### 4.1 매출: 분기 합계와 점포당 월평균의 차이

로컬 보고서는 처음에 `추정매출액 (분기 합계)`를 요약 카드에 표시했다. 서울시 간략보고서의 대응 카드는 `매출액 (점포당 월평균)`이다. 비교 대상 자체가 달라 큰 차이처럼 보였다.

```text
점포당 월평균 추정매출(원) = 해당 분기 추정매출액 합계(원) ÷ 3개월 ÷ 해당 분기 점포수
전분기/전년 동분기 증감액 = 두 분기의 점포당 월평균값 차이
```

화곡1동의 2026년 2분기 로컬 CSV 합계는 약 **837.1억 원**, 점포수는 **2,337개**다. 이를 환산하면 **1,194만 원**으로 서울시 화면의 현재값과 일치했다. 전분기 대비도 **−14만 원**으로 일치했다. 전년 동분기 대비는 CSV를 반올림하면 **+28만 원**이고 공식 화면은 **+27만 원**이었다. 따라서 단위 환산만으로 모든 증감액이 같아지지는 않는다.

### 4.2 같은 단위인데도 매출이 다른 사례

잠실4동은 점포수 **441개**와 단위가 같아도 로컬 CSV 환산값이 **999만 원**, 서울시 간략보고서는 **1,003만 원**이었다. 공식 화면은 전분기 대비 **−60만 원**, 전년 동분기 대비 **−184만 원**도 표시했다. 서울시 순위 API는 TOP 10만 반환하므로 잠실4동의 공식 매출 표시값은 기존 순위 스냅샷에 없었다.

**해결:** 확인된 보고서 표시값을 분기별 `data/official-report-sales-20262.json`에 기록하고, 해당 지역 요약·매출분석에서는 그 값을 우선 사용한다. 현재 이 파일은 대화에서 직접 확인한 **잠실4동과 화곡1동**만 포함한다. 다른 지역은 순위 스냅샷에 매출액이 있으면 이를 3개월·점포수로 환산하고, 없으면 CSV 합계를 환산한다. 공식 보고서의 전 지역 수치를 추정해 만들어 넣지 않는다.

### 4.3 유동인구: 총량과 면적당 인구의 차이

로컬 CSV의 유동인구는 분기 총량이고, 원본 간략보고서의 카드는 `3개월간 1ha당 인구수`다.

```text
분석 면적(ha) = 서울시 분석 면적(㎡) ÷ 10,000
유동인구 밀도(명/ha) = 분기 유동인구 수 ÷ 분석 면적(ha)
```

서울시 순위 응답의 분석 면적을 저장해 보고서 요약에 사용한다. 송천동은 환산 결과 **118,254명/ha**가 공식 화면과 일치했고, 전분기 차이 **+73명/ha**도 테스트로 확인했다. 분석 면적을 확보하지 못한 지역은 `명/ha`로 추정해 표시하지 않고 분기 총량으로 표시한다.

### 4.4 점포수와 상주인구

점포수는 업종별 `전체_점포_수`를 지역별로 합산한다. 상주인구는 별도의 행정동별 원본 수치를 사용한다. 일원본동 점포수 **462개**, 화곡1동 상주인구 **50,743명**을 공식 화면 사례와 대조했다. 매출·유동인구와 달리 이 두 사례의 현재값은 단위 변환 없이 일치했다. 이것이 모든 지역·과거 분기의 완전한 일치를 보장하지는 않는다.

## 5. 상세조건 구현과 기준

상세조건은 `frontend/pages/rising/index.html`, `frontend/pages/rising/main.js`, `backend/server/data.js`에 연결했다. 화면에서 선택을 바꿀 때는 임시 상태만 갱신하고 **적용**을 눌러야 목록·지도 순위가 다시 조회된다. **취소**는 적용 전 상태로 되돌린다. 기본값은 서울시 화면과 같은 `비교증가율 / 최신 분기 / 전분기 / 전체 업종`이다.

| 조건 | 현재 동작 |
| --- | --- |
| 최고순위 | 현재 수치가 큰 지역 순 |
| 비교증가율 | 비교 기준 대비 증가율 순 |
| 비교절대값 | 비교 기준 대비 증가량 순 |
| 조회분기 | 전분기 또는 전년 동분기와 비교 |
| 기준년도 | 보유한 연도의 같은 분기 자료로 비교. 유량 지표인 매출·유동인구는 비교 가능한 분기를 합산하고, 점포·상주인구는 마지막 분기를 사용 |
| 업종 | 전체·외식업(`CS1`)·서비스업(`CS2`)·소매업(`CS3`). 업종별 원본이 있는 점포수·매출에만 적용 |

업종 버튼은 원본 화면처럼 네 칸을 가로로 배치하고 글자 오른쪽에 아이콘을 놓았다. 현재 원본은 **2025년 1분기~2026년 2분기**이므로 2023·2024년 버튼은 비활성화된다. 업종별 세부 자료는 최근 5개 분기만 있으므로 그 이전 업종 비교도 제한된다. 기본 조건 이외의 순위는 공식 순위 API의 결과가 아니라 로컬 원본 집계 결과다.

## 6. 검증과 재현

```powershell
npm run fetch:dong       # 행정동별 공개 CSV와 경계 자료 내려받기
npm run import:raw       # 상권 ZIP + 행정동 CSV를 SQLite로 적재
npm run import:details   # 이미 만든 DB의 보고서 세부 열 갱신
npm run sync:rankings    # 최신 분기 기본 순위 응답 동기화
npm run test:rankings    # 사례별 회귀 테스트
npm run dev              # 로컬 서비스 실행
```

`npm run test:rankings`에는 강남·중랑 순위, 강동구 매출 순위 표시값, 송천동 유동인구 밀도, 신길1동 매출·유동인구, 화곡1동 점포당 월평균, 잠실4동 보고서 표시값, 업종·비교기간별 순위가 포함된다. 테스트는 `data/commerce.sqlite`가 없으면 일부 항목을 건너뛰므로, 검증 전에 원본을 적재해야 한다.

## 7. 현재 남은 한계와 다음 점검 지점

- **공식값의 범위:** 기본 TOP 10 스냅샷과 수동으로 확인한 보고서 매출 외에는 공식 화면과 전 지역을 자동 대조하지 않았다. 특히 잠실4동처럼 CSV와 공식 보고서가 다른 지역이 더 있을 수 있다.
- **분기 갱신:** 공식 순위 스냅샷은 특정 분기 파일이다. 다음 분기 원본을 적재한 뒤 다시 동기화하고 순서·표시값·면적 테스트를 갱신해야 한다. 수동 보고서 매출 파일은 자동 동기화되지 않는다.
- **상세조건의 비교:** 기본 조건 외 순위는 CSV 계산 결과다. 공식 서비스의 추가 필터·보정 로직과 완전히 같은 결과라고 주장하지 않는다.
- **원본 범위:** 2023·2024년 분기, 일부 행정동 세부 지표와 생존율 자료가 없다. 자료가 없으면 빈값·제공되지 않음으로 표시한다.
- **지도 경계:** 행정동 코드와 경계 버전이 다른 곳은 경계 표시를 별도로 보정해야 한다. 원형 배지는 실제 지역 경계가 아니다.
- **종합의견:** Ollama 문장은 생성 결과이므로 보고서의 원본 수치와 대조해 사용한다. 서버에 연결할 수 없을 때는 CSV 수치 요약으로 돌아간다.

핵심 원칙은 **같은 지표명이라도 집계 범위·단위·분모·기준분기·출처를 먼저 대조하는 것**이다. 화면의 숫자를 맞추기 위해 근거 없는 보정률을 적용하거나 누락된 값을 임의 생성하지 않는다.
